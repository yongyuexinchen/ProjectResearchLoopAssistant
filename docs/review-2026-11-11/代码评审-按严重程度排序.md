# 代码与架构评审：按严重程度排序

日期：2026-11-11。原始评审基线：[6b66b51c357fc893bb52c4d22d34777d09af4125](https://github.com/yongyuexinchen/ProjectResearchLoopAssistant/tree/6b66b51c357fc893bb52c4d22d34777d09af4125)；本地 HEAD 与公开 main 一致，开始时工作区干净。先读 STATUS、ARCHITECTURE、README；用户提供的教程只用于理解图的呈现风格，未把其中操作要求视为本次指令。

以下行号均指原始基线，后续新增源码图功能会改变文件行号。审阅结果不等于已修复清单。

## 判定口径

- **静态事实**：源码存在的判断、查询条件、调用位置或语法结构。
- **复现观察**：额外离线实验确实观察到的结果；说明使用的数据库和注入点。
- **影响推断**：从上述事实推出的后果，未实际发生的生产故障不写为事实。
- **P1**：优先处理，破坏关键运行互斥/状态隔离；**P2**：明确实现缺陷，特定输入或时序可触发；**P3**：较低影响的错误结论、审计重复或输入报错。没有确认 P0。
- 只读代码扫描不等于运行验证，文件存在不等于测试有效，合法 evidence id 不等于该证据支持正文。

## 总体判断

五种调研方式确实有不同的章节、分析分支、质量权重和专项检查；它们共享同一个扫描器和同一类事实，不能当作五套独立代码理解算法。原有目录图/组件图有结构依据，原时序图和分层数据流仍是启发式阅读骨架。源码中的证据约束存在实际旁路，Worker 也存在具体取消/接管时序漏洞。

报告的“已保存正文”与“按旧 run 再生成”应区分：前者固定保存；后者目前仍读取全项目历史资料。架构图的已保存快照及单图修复保持旧 run 的结构，属于验证成立的正向结果。

## 问题清单

### 1. [P1] 人工评审绕过互斥，历史或重复评审可启动并行任务

定位：`services/api/app/services/reports.py::review_report_snapshot` L459–496；`api/routes_reports.py::review_report` L131–152。

**事实**：评审无当前运行/active job 检查，直接覆盖 project.status；needs_more/rejected 先改 ready，再调用只按项目状态保护的 enqueue_run；同一报告重复提交会重复入队。**复现**：B 正在 running 时对 A 连续 approved、needs_more、needs_more，三个 HTTP 都 200，最终 active jobs 为 running+queued+queued。**推断**：并行 Worker 可竞争共享项目状态和采集上下文；未启动并行 Worker 进行真实故障注入。

建议：在项目锁内检查当前运行，历史评审不得改当前项目状态，follow-up 入队使用稳定幂等键。详见 [IF-01](isolation-frontend-review.md)。

### 2. [P2] 旧 Worker 的收尾能覆盖新 Worker 已取得的租约

定位：`workers/run_worker.py::run_one_job` L70–100；`services/run_jobs.py::mark_job_failed` L158–161。

**事实**：普通读校验 owner 后无条件修改任务/运行状态，没有原子条件更新或 fencing token。**复现**：两个临时文件 SQLite 会话，B 已接管 running/worker-b 后，A 的错误收尾仍写成 failed/owner=None。**推断**：B 的后续 guard 会停止，而该 job 不再自动恢复。未验证真实 InnoDB 并发调度。

建议：成功/失败收尾在同一短事务中做 owner+attempt 条件更新，只有胜出的 owner 才能更改 run/project。详见 [Worker P2-3](worker-review.md)。

### 3. [P2] 重试复用 analysis 时覆盖取消状态，任务可能卡在“运行中”

定位：`workers/run_worker.py::execute_workflow` L221–226。

**事实**：恢复 ready 状态并 commit，发生在 reuse_stage 的 guard 之前。**复现**：后续阶段失败后 retry，在已完成 collection 的复用检查之后取消，cancel=200，最终 run=ready_for_review_with_risks、workflow=running、retry job=cancelled、无报告。内存及临时文件 SQLite 均观察到。**推断**：没有 active job，retry/resume 的状态约束又拒绝继续该 run。

建议：状态写入也受同一原子取消/owner 检查保护，不要先提交再 guard。详见 [Worker P2-1](worker-review.md)。

### 4. [P2] 普通 run 的恢复在 HTTP 内同步执行，取消保护没有接入

定位：`api/routes_runs.py::resume_existing_run` L172–188；`engine/runner.py::resume_run` L119–146；`langgraph_runner.py::resume_run_graph` L75–92。

**事实**：仅 workflow 恢复入队；普通 run 直接执行 graph，未注入 _GRAPH_GUARD。**复现**：恢复中 cancel=200，active jobs=0，随后继续写分析等多个节点并将 cancelled 覆盖为 ready_for_review_with_risks。**推断**：API 进程退出时没有 durable resume job 可由 stale-job recovery 接手；本次未终止真实 API 进程。

建议：统一恢复入队并通过带 guard 的 graph streaming 路径执行。详见 [Worker P2-2](worker-review.md)。

### 5. [P2] Checkpointer 的 pending writes 索引与 LangGraph 契约不兼容

定位：`engine/checkpointer.py::SqlAlchemyCheckpointSaver.put_writes` L150–165。

**事实**：所有 channel 都用 enumerate 从 0 编号，已有项直接跳过；实际依赖对 error/interrupt/resume 等使用保留负索引并有更新语义。**复现**：相同 checkpoint/task 先写 __error__ 后写 score，项目 saver 只保留 error，依赖自带 InMemorySaver 同时保留 error 和 score。**推断**：后继完整 checkpoint 前再次崩溃时，成功输出无法从 pending writes 恢复，可能重复执行节点；不代表全部正常 resume 失败。

建议：遵守锁定依赖的 WRITES_IDX_MAP 和更新规则，增加契约及故障注入测试。详见 [Worker P2-4](worker-review.md)。

### 6. [P2] 模型能自造无来源 evidence，再用它证明自己的结论

定位：`llm/analyzer.py::_validate_evidence_items` L149–168、`validate_llm_analysis_output` L227–230；`verifiers/package.py` L335–359。

**事实**：新 llm:* evidence 不要求采集来源，自动加入 allowed refs；verifier 只看 id 属于包。**复现**：虚构“已生产部署且测试通过”的 evidence、仅引用它的 finding，validator accepted，证据覆盖检查也通过。**推断**：错误模型输出可披上“确定性证据检查通过”的外观。

建议：模型产物作为 advisory；若允许派生证据，强制 derived_from 到非模型采集证据并验证祖先链。详见 [E1](evidence-review.md)。

### 7. [P2] 智能报告摘要有零引用旁路

定位：`reports/llm_generator.py::validate_llm_report_sections` L58–70、118–120；`merge_llm_report_markdown` L176–189。

**事实/复现**：allowed evidence 为空时，executive_summary 写“生产部署和所有测试通过”、sections=[] 仍 accepted，并进入正文。不是泛化要求程序证明自然语言语义，而是结构化引用检查被完全绕过。

建议：摘要增加显式 refs 并校验，或只能从已验证 section 生成。详见 [E2](evidence-review.md)。

### 8. [P2] 按 run 再生成报告仍混入项目其他版本资料

定位：`services/reports.py::build_inventory` L622–643、报告创建 L60–65、智能上下文 L100–109；`context/builder.py::build_analysis_context` L15–27。

**事实**：分析产物按 run，但 source snapshots/maps 无 run 绑定、只按 project 取所有历史记录。**复现**：OLD_VERSION 改成 NEW_VERSION 并再采集后，重建 A 含 NEW，新 B 仍含 OLD；智能 prompt 也含未来标记。已保存 A 正文保持原样。**推断**：旧结论/新资料可能在同一报告互相矛盾，最新采集失败时旧地图仍可参与分析。

建议：run 固定采集 id 集合，分析、报告和模型上下文统一使用；仅以报告创建时间截断不够。详见 [IF-02](isolation-frontend-review.md)。

### 9. [P2] 历史报告页的生成按钮没有传所选 run

定位：`apps/web/app/projects/[id]/report/page.tsx` L19–30、337、346–347；后端 `services/reports.py::get_run_for_report` L571–575。

**事实**：历史页加载 A，但生成 helper 未收到 A.run_id；省略时后端选最新 B。**证据**：参数链及服务层选择规则已核实；未使用浏览器复现原始按钮。**影响**：用户在 A 页操作得到 B 报告，B 尚未结束则生成失败。

建议：绑定 report.run_id 并跳到新 report_id。此项在本轮报告含图实现中一并修复，最终验收见功能验证记录。详见 [IF-03](isolation-frontend-review.md)。

### 10. [P2] 公网网页重定向能越过到运行机内网

定位：`core/security.py::_validate_web_url` L38–55；`tools/web_tools.py::fetch_web_url` L53–58。

**事实**：采集自动跟随跳转，不复核目标 IP/边界。**复现**：MockTransport 公网 URL 302 到 127.0.0.1/private，被跟随且内部文本进入摘要。没有访问真实内网。**推断**：摘要可能随之后模型增强外发；没有真实模型外发实验。

建议：默认全局公网地址策略，逐跳/DNS 复核与跳转上限，内网读取需显式边界。详见 [IF-04](isolation-frontend-review.md)。

### 11. [P2] 网页只截断最终摘要，完整响应下载没有字节预算

定位：`tools/web_tools.py::fetch_web_url` L53–74。

**事实/复现**：client.get 先下载，HTMLParser 保存全页文本，最后才截断。摘要长度 10 的情况下仍读取 8 MiB / 128 块。**推断**：大页面或连续流可占用 Worker 内存/时间；timeout 不是总字节预算。

建议：流式读取时累计字节并中止，限制解压后内容与解析量。详见 [IF-05](isolation-frontend-review.md)。

### 12. [P2] 缺 README 被确定性分析写为已有 README

定位：`engine/profile_analysis.py::readme_excerpt` L476–477；引用处 L70–81、414–430。

**事实/复现**：None 变成非空字符串 "None"；真实无 README 小仓库生成“已具备项目说明材料”和交付 README 已具备。**影响**：同份报告的缺口与发现互相矛盾。

建议：保留 None/空文本语义并测缺键、None、空白、正常值。详见 [E3](evidence-review.md)。

### 13. [P2] 标准 Go 测试漏检，错误提高改造/验收风险

定位：`tools/code_scan_tools.py::is_test_file` L292–303。

**事实/复现**：`pkg/hello_test.go` 返回 False；Go 是项目声明支持的扫描语言。**推断**：报告把有标准测试的项目写成没有自动化测试，后续二开成本与练习安排失真。

建议：支持 *_test.go 并覆盖分类函数的下游消费者。详见 [E4](evidence-review.md)。

### 14. [P2] 多地图聚合发现引用第一份地图，id 有效但来源错误

定位：`engine/profile_analysis.py` L28–37、119–130、480–485。

**事实/复现**：聚合 m1/main.py 与 m2/server.js/package.json 的发现只引用 m1。**影响**：点击该证据无法支持跨库断言；同一源的历史多地图也可触发。

建议：按 map/source 生成发现，或收集所有参与来源 refs。详见 [E5](evidence-review.md)。

### 15. [P2] 原 UML 类图将不同文件同名类合成一个节点

定位：`architecture/uml.py::build_class_diagram` L94–116。

**事实/复现**：a.py、b.py 的 Config 都生成 c_Config，Mermaid 合并方法；短名称继承索引也可能串线。**影响**：图中出现不存在的类结构。新增 source_flow 使用独立身份设计，不代表原 UML 类图本项已修复。

建议：路径+限定名身份，继承无法解析时不按全局短名猜测。详见 [E6](evidence-review.md)。

### 16. [P3] 业务 commit 与 checkpoint 分离，崩溃后重复评分和轨迹

定位：`langgraph_runner.py::verify_package_node` L624–667、`commit_graph_step` L231–237；`checkpointer.py` L50–57、191–194。

**事实**：两个独立事务，不具备“节点副作用 exactly-once”。**复现**：原评分函数 commit 后、返回 LangGraph 前注入 KeyboardInterrupt，过期恢复后 score/verify turn 各两条，delta 从 93 变 0，run 最终完成。**推断**：模型调用有同类重放窗口，但未验证重复计费，不能把它写为已发生损失。

建议：节点稳定执行键与幂等结果，或统一提交策略。详见 [Worker P3-1](worker-review.md)。

### 17. [P3] 文件存在性被写成低回归/配置成本

定位：`reports/renderer.py::render_test_config_complexity` L822–837。

**事实**：有任意测试路径就写回归成本低，少量配置/技术栈标签决定其他低成本等级。**影响推断**：空测试或不覆盖改造点的测试不能支撑成本结论。

建议：报告“存在测试文件，成本待确认”，启发式等级必须显式标注。详见 [E7](evidence-review.md)。

### 18. [P3] 安全策略跳过 .env.example 后又断言样例不存在

定位：`tools/path_policy.py` L33–35、79–87；`reports/renderer.py` L1101–1105。

**事实/复现**：skipped_items 有 .env.example，但缺口只读 file_tree，断言未发现。建议写“路径存在，内容按策略未采集”。不要求解除敏感内容保护。详见 [E8](evidence-review.md)。

### 19. [P3] 非法 IPv6 URI 绕过预期异常转换，setup 返回 500

定位：`core/security.py::_validate_web_url` 的 urlsplit；`api/routes_workflow.py::setup_project` L20–23。

**事实/复现**：`https://[::1` 引发 ValueError，调用层只捕获 SourceValidationError，TestClient 关闭 raise_server_exceptions 后为 500。建议转换解析异常并覆盖非法 bracket/port 输入。详见 [IF-06](isolation-frontend-review.md)。

## 测试盲区与性能风险

原始基线实跑：后端 **333 passed, 1 skipped**（20.46 秒）；前端 **15 passed**；TypeScript **通过**。各专项额外探针范围见链接报告。没有运行真实 MySQL、真实 Worker kill -9 / Windows 进程终止压测、真实模型调用或大仓库规模 benchmark。

| 范围 | 静态事实 | 仍需验证的事项 |
| --- | --- | --- |
| MySQL | CI 无 MySQL service；test_mysql_checkpointer 实际 SQLite；guard 为 StaticPool 另走分支 | InnoDB SKIP LOCKED、FOR UPDATE、独立连接可见性、迁移空库升级、真实 JSON 往返 |
| 事件序号 | savepoint 冲突后读 MAX(sequence) 重试 | MySQL REPEATABLE READ 旧视图可能持续冲突；这是风险，尚未复现 |
| 崩溃恢复 | 有 lease/checkpoint，也有上列窗口 | 真进程崩溃、连接中断、恢复时再次崩溃、长模型调用重放 |
| 采集/大仓库 | per-file 大小过滤存在，但 scan_codebase 的文件树/历史清单整体积累；图有局部扫描预算 | 大文件数的遍历时间、文件树 JSON/DB 写入体积、完整 context 多次复制/checkpoint 内存、历史资料增长 |
| 前端 | 15 项基线主要测纯工具函数，非向导和报告实际交互 | 粘贴/切类型/提交失败保留、非法 URI、历史 run 按钮、浏览器图渲染与PDF可读性 |
| 模型 | 自动测试使用 fake/skipped | provider 超时/非法JSON/长上下文/失败回退；不能因输出有引用就认定语义真实 |

优先补测试顺序：运行互斥与评审幂等 → 取消/接管 fencing → saver 契约 → run 固定采集版本 → 来源链与摘要引用 → MySQL 双连接故障注入 → 有预算的大规模 benchmark。
